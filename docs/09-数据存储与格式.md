# AnimatedScroll 数据存储与格式

按当前代码整理（2026-10-31）。示例为虚构ID和字段节选，用于理解结构，不能直接作为完整项目恢复文件。路径均相对项目根目录。

## 1. 保存在哪里

| 位置 | 内容 |
| --- | --- |
| `data/projects.sqlite` | SQLite；项目、版本快照、操作日志、后台任务 |
| `data/<文件名>` | 上传画作、TXT/MD、PDF及资料图片；数据库只保存文件名或访问路径 |
| `data/portraits/<hash>.jpg` | 人物裁切缓存，按画作路径、图片版本及框坐标生成 |
| `data/backups/` | 本地迁移备份 |
| `models/`、`.runtime/` | 检测模型缓存、服务PID及运行日志；不是创作内容 |
| 环境变量或本机 `.env` | API Key等服务配置；不写入项目、研究日志或Git |

数据库不是“每个人物一张表”，而是**每个项目保存一个完整JSON**：

| 表 | 主要列 | 保存方式 |
| --- | --- | --- |
| `projects` | `id, body` | `body`为整个项目JSON |
| `events` | `id, project, time, action, before, after, meta` | 操作前后项目快照和元数据；JSON以TEXT保存 |
| `tasks` | `id, project, body` | 检测、视觉匹配、OCR、资料整理任务JSON |
| `studio_jobs` | `id, project, body` | 剧情、线索、知识、分镜等生成任务JSON |
| `document_cache` | `key, body` | 已通过校验的文献批次及摘要；按原文、目标、提示词与校验版本缓存，不存密钥或思考内容 |

数据目录可通过 `CREATION_DATA_DIR` 修改。备份应包含整个 `data/`，不能只复制图片或单份项目JSON。关闭服务后复制可保持数据库一致。

## 2. 项目与统一条目结构

制作数据位于 `project.workspace`，格式版本为 `"2.0"`。项目根级还保留导入数据及旧接口的 `characters/scenes/intent/checks`；新版剧情、知识、线索和分镜以 `workspace.entities` 为准，不能假设旧字段与新版一一同步。

```json
{
  "id": "project-1",
  "title": "折槛图创作",
  "version": 12,
  "workspace": {
    "schemaVersion": "2.0",
    "entities": {},
    "folders": [],
    "consistencyChecks": []
  }
}
```

`entities`使用 `kind:id` 作为键，例如 `character:char-1`。所有业务条目使用同一外壳：

```json
{
  "id": "char-1",
  "kind": "character",
  "draft": {"name": "朱云"},
  "published": null,
  "revision": 0,
  "state": "draft",
  "refs": [{"key": "material:main", "revision": 1}],
  "history": []
}
```

- `draft`：已保存草稿；`published`：最近人工确认版本，**不是对外发布**；首次确认前为`null`。
- `refs`：所依赖条目的键及确认版本；`history`保存被替换的确认版本。操作全过程另有`events`快照。
- ID使用稳定字符串，改名不换ID，不以姓名或数组下标作关联；日志时间采用UTC的ISO 8601格式。
- 持久化状态：`draft`待确认、`confirmed`已确认、`stale`／`review`为旧兼容状态，普通版本变化由独立版本提醒表示、`deleted`软删除。
- `changed`改动待处理、`waiting`等待前置条件、`missing/incomplete`等是界面或检查计算结果，不是另一份确认记录。

## 3. 各部分字段与 sample

### 0 概览

流程说明是前端静态内容，没有单独业务数据。浏览器`localStorage`只记当前项目ID；未保存编辑、选中项、抽屉和返回位置在前端内存中，不应当作已持久化内容。

### 1 古画资料库

根级保存`image/imageVersion`、`materialInputs`、`sources`、`documents`、`annotations`、`observations`、`matches`；整理结果为`materialSegments/materialAnalysis`。对应的`material:main`草稿／确认版本保存图片、三段原文、来源、框、观察及匹配的版本快照。

```json
{
  "image": "/api/images/painting-1.png",
  "imageVersion": 1,
  "materialInputs": {"background": "宋代画作表现汉代故事。", "relationships": "朱云曾任槐里令。", "narrative": "", "version": 1},
  "sources": [{"id": "source-1", "title": "人物与关系", "text": "朱云曾任槐里令。", "citation": "用户提供的资料", "location": "人物与关系", "version": 1, "method": "material_input", "materialKind": "relationships", "confirmed": true}],
  "materialSegments": [{"id": "segment-1", "kind": "relationships", "quote": "朱云曾任槐里令。", "summary": "朱云身份", "start": 0, "end": 8, "sourceId": "source-1", "sourceVersion": 1, "inputVersion": 1}],
  "materialAnalysis": {"inputVersion": 1, "stale": false, "summary": "人物资料摘要", "characters": [], "eventFramework": []}
}
```

**规范：**保留完整原文；`narrative`为空则是基于背景共创，不另存模式开关。位置采用Python字符下标，`start`包含、`end`不包含，须满足`原文[start:end] == quote`。资料已确认只表示人工核对，不代表系统独立证明史实。

文件导入元数据例：`documents`中的`filename`对应`data/`下实体文件，`format`为`text/pdf/image`，页码从1开始；文件提取/OCR文本进入`sources`，有`documentId/page/method/confirmed`用于追踪。

```json
{"id": "document-1", "filename": "document-1.pdf", "title": "补充资料.pdf", "citation": "资料出处", "format": "pdf", "pageCount": 1, "pages": [{"page": 1, "text": "提取的原文"}]}
```

新版PDF记录另有`contentHash/sizeBytes/parseStatus/parseVersion`，`parseStatus=queued/ready`；解析失败和中断状态在任务中。逐页增加稳定`id`、`engine=pdfium/pypdf/failed`、`quality={state,characters,imageCount,warning}`；质量状态为`ready/review/image_page/blank`，不是史实确认。上传分块落盘，PDF限100MB、300页；本地解析不调用LLM。

文献整理提案位置为根级`documentAnalysis`，字段节选：

```json
{
  "id": "analysis-1", "status": "pending", "targetArtwork": "画甲", "inputHash": "<sha256>",
  "request": {"targetArtwork": "画甲", "documents": [{"documentId": "document-1", "pages": []}]},
  "claims": [{"id": "claim-1", "kind": "background", "text": "论文描述画中人物持卷。", "assertion": "description", "indirectSource": "", "references": [{"sourceId": "source-p1", "sourceVersion": 1, "documentId": "document-1", "page": 1, "start": 0, "end": 7, "quote": "画中人物持卷。"}]}],
  "people": [{"id": "person-candidate-1", "name": "持卷者", "scope": "depicted", "artwork": "画甲", "contextRoles": ["depicted"], "references": [], "depictionReferences": [], "visualHints": [], "accounts": []}],
  "summaries": {"background": [{"text": "论文描述画中人物持卷。", "claimIds": ["claim-1"], "references": []}], "relationships": [], "narrative": []},
  "coverage": [{"batch": 1, "pages": [{"documentId": "document-1", "page": 1}], "cached": false}],
  "selectedPages": [{"documentId": "document-1", "page": 1, "hasText": true}], "modelCalls": 2, "promptVersion": "literature-1"
}
```

上例为字段节选，实际人物、摘要和身份提示必须带有效引用，不能使用空引用采用。`assertion`为`description/historical_account/interpretation/uncertain`；`scope=depicted/background/unknown`。人物的`contextRoles`区分`depicted/historical_background/creator/inscriber/collector/scholar/other_artwork/uncertain`；同一人可兼具作者和画中人物身份，判断以本画引文为准。`accounts`保留不同批次记载；`aliasQuestions`保留未足以合并的称呼及理由。

`claims[].topic`另记录用途：`culture/people_relationship/story/artwork_metadata/artwork_history/comparison/research/uncertain`，不替代真实性。三段摘要按用途隔离生成，`validationWarnings`保存被排除的无效引文及待核对信息（字符串或诊断对象）。缓存还包含用途分类和各段摘要，校验版本变化时重新校验。完整可读的通用样例见[文献样例](../examples/literature-sample.json)。

采用后`status=adopted`，根级`materialInputOrigins`按三段类型保存`analysisId/textHash/references/paragraphs/claims`。对应`material_input`来源标为`sourceType=derived_summary`，不能作为有依据单元的原始引用；必须使用PDF页来源。人工编辑摘要后，`textHash`不符则标为待复核。采用的角色`namingOrigin=document`，只有`depictionScope=depicted`者默认进入档案；其提及和视觉提示直接关联原页。

框、观察、姓名匹配是不同对象，分别存入三个数组：

```json
{
  "annotations": [{"id": "box-1", "kind": "character", "characterId": "char-1", "x": 0.1, "y": 0.2, "w": 0.2, "h": 0.4, "description": "一名男子立于殿前", "confirmed": false, "identityConfirmed": true, "needsReview": false}],
  "observations": [{"id": "observation-1", "annotationId": "box-1", "description": "一名男子立于殿前", "inference": "可能正在发言", "confirmed": false}],
  "matches": [{"id": "match-1", "annotationId": "box-1", "characterId": "char-1", "reason": "人工指定", "confirmed": true, "manual": true, "stale": false}]
}
```

坐标`x/y/w/h`均相对整张画归一化到0—1，表示左上角及宽高，框不应越界；`faceRegion`也使用全图坐标。画面观察确认与姓名对应确认独立，同一角色可对应多个画中实例。裁切图可重新生成，不作为人物身份的唯一依据。

`identityManual`表示人工选择／命名，`geometryManual`表示人工调整过框；重新检测和匹配保留这些人工结果。视觉补检存独立提案，不立即写入`annotations`：

```json
{"visualDetectionProposal": {"taskId": "task-1", "image": "/api/images/painting-1.png", "imageVersion": 1, "inputHash": "<sha256>", "status": "pending", "candidates": [{"id": "candidate-1", "x": 0.6, "y": 0.2, "w": 0.1, "h": 0.4, "description": "坐姿人物", "origin": "vision_supplement", "kind": "character", "characterId": "", "confirmed": false}]}}
```

`POST /api/projects/{id}/detections/adopt`携带`version/taskId/candidates`；候选可修改坐标或删去，必须属于当前提案，且图片、已有框的输入摘要仍有效。采用后`status=adopted`并记录`adoptedIds`，不触发匹配。

匹配结果增加`confidence/features/supports/constraintChecks/conflicts/alternatives`。`supports`引用有效来源或该角色的视觉提示；`constraintChecks`记录`hintId/result/evidence`，`result`为`supports/conflicts/unknown`。存在明确冲突、必要提示未支持、非高把握或无有效依据时，`characterId`留空。它们是模型建议，不是独立核实结果。

### 2 人物档案与人物知识

人物资料：`character:<角色ID>.draft`。身份、经历和关系只概括输入内容；缺失留空。`namingOrigin`常用`material`（资料提取）、`creator`（创作者命名）、`legacy`（旧数据）；`mentions`追溯原文。

新增`identityOptions=[{label,assessment,references}]`记录同一人物的身份解释，`assessment=certain/likely/possible/rejected`。引用必须先逐字绑定原文；PDF在全文合并后判断：只有一个有效身份解释，且至少有一项`certain/likely`，才生成`creativeNaming`。三段输入采用同一规则。不同解释并存、弱猜想或人物范围不明则不生成，不自动补名。

合成样例（来源全文为“画中持卷者很可能是礼仪官。”）：

```json
{
  "name": "礼仪官", "identity": "礼仪官", "sourceName": "持卷者", "confirmed": false,
  "creativeNaming": {
    "name": "礼仪官", "sourceName": "持卷者", "sourceIdentity": "礼仪官（推测）",
    "basis": "literature_interpretation", "policyVersion": "single-preferred-identity-1",
    "references": [{"sourceId": "source-1", "sourceVersion": 1, "quote": "持卷者很可能是礼仪官", "start": 2, "end": 12}]
  }
}
```

`basis=document_identity/literature_interpretation`区分明确记载与用于创作的身份解释。创作称谓可用于剧情称呼，原判断不因此升级为历史事实。原画面称谓参与已有角色的采用查找，更新仍要求`updateIds`，不以创作称谓伪造历史别名或创建重复角色。

```json
{
  "name": "朱云", "identity": "曾任槐里令", "biography": "",
  "summary": "资料中记载朱云曾任槐里令。", "relationships": "", "evidence": "需核对输入资料",
  "namingOrigin": "material",
  "roleType": "named", "depictionScope": "unknown", "visualHints": [],
  "mentions": [{"kind": "relationships", "quote": "朱云曾任槐里令。", "start": 0, "end": 8, "sourceId": "source-1", "sourceVersion": 1}],
  "faceRegion": {"x": 0.12, "y": 0.21, "w": 0.06, "h": 0.08}
}
```

`roleType`为`named/role/group/unknown`；`depictionScope`为`depicted/background/unknown`。旧数据缺失按`unknown`处理，不在打开时调用模型。人物称谓和群体也有稳定角色ID，可关联多个实例。视觉身份提示仅提取原文，例：

```json
{"id": "hint-1", "kind": "relationships", "quote": "典礼官身穿红袍", "text": "红袍", "attribute": "clothing", "value": "红袍", "strength": "required", "exclusive": false, "sourceId": "source-2", "sourceVersion": 1, "inputVersion": 1, "start": 0, "end": 7}
```

`strength=required/suggested`；`exclusive`仅用于原文明示排他条件。提示的来源版本和逐字引文须有效；不能把模型观察当作原文提示。

人物知识：`knowledge:<角色ID>.draft`，独立确认，**不是自由填写的人物背景文本**。绑定已确认线索，可存模型`suggestion/suggestionRefs`，供人工采用。

```json
{"characterId": "char-1", "clueIds": ["clue-n1"], "reasons": {"clue-n1": "人物参与该情节，可获知此信息"}}
```

首次没有已确认线索时显示“等待线索确认”，不计立即待办；确认人物资料不会同时确认知识。旧字段`knowledge/legacyText`仅为兼容，不代替新版线索绑定。

### 3 剧本大纲

创作设置：`intent:main.draft`。历史框架、允许虚构、禁止内容均为字符串数组；`plotCount`为1—12。

```json
{"theme": "进谏与容言", "audience": "博物馆普通观众", "tone": "克制、生动", "goal": "表现进谏冲突", "framework": ["保留输入材料中的主要事件顺序"], "fiction": ["允许补充过渡动作"], "forbidden": ["不编造人物既往经历"], "plotCount": 1}
```

剧情：`plot:plot-1.draft`。以ID关联人物和子叙事线索；`region`可为`null`或归一化矩形。

```json
{"title": "当廷请剑", "goal": "呈现冲突开端", "body": "朱云入殿陈述，并提出请求。", "connection": "引出皇帝的回应", "characterIds": ["char-1"], "clueIds": ["clue-n1"], "region": {"x": 0.1, "y": 0.2, "w": 0.5, "h": 0.5}}
```

每个剧情至少有一条自己的子叙事线索。`plot_clues`任务仅追加子线索草稿，不改写剧情正文、不自动确认。

### 4 线索库

分类在`workspace.folders`中，`parentId`组成树，叶子是`entities`中的线索。三个根固定为`culture/relationship/narrative`，不能删除或互相嵌套；中间分类不能形成循环。

```json
[
  {"id": "culture", "name": "文化背景", "type": "culture", "parentId": "", "root": true},
  {"id": "relationship", "name": "人物关系", "type": "relationship", "parentId": "", "root": true},
  {"id": "narrative", "name": "叙事线索", "type": "narrative", "parentId": "", "root": true}
]
```

叙事线索：`clue:clue-n1.draft`，业务编辑仅需标题、所属剧情和一段情节。`plotIds`为兼容保留的数组，**确认时必须且只能有一个ID**；人物从剧情继承。

```json
{"name": "入殿陈述", "type": "narrative", "parentId": "narrative", "plotIds": ["plot-1"], "characterIds": ["char-1"], "content": "朱云走到殿前，向在场众人陈述自己的请求。"}
```

服务端会将新编辑的`content`同步到`summary`及一个`fiction`类型的内部`units`，不自动称其为史料原文。旧线索仍可由多个旧单元合并显示；原内容和依据保留于`legacyUnits`及操作历史。锁定内容须先解锁保存。

文化背景、人物关系仍采用`summary + characterIds + units`。内部单元sample如下：

```json
{"id": "unit-1", "text": "朱云曾任槐里令。", "kind": "clue", "category": "supported", "speakerId": "", "rationale": "", "references": [{"sourceId": "source-1", "sourceVersion": 1, "quote": "朱云曾任槐里令。"}], "status": "pending", "locked": false}
```

`kind`：`event/action/dialogue/clue`；`category`：`supported/inference/fiction`；`status`：`pending/approved/rejected`。有依据和推测须有有效引用；推测还需`rationale`。画面引用使用`annotationId + quote`且观察须确认；逐字引文和来源版本必须匹配。单元审核状态与整个条目的确认状态不是同一字段。

### 5 分镜管理

位置：`storyboard:clue-n1.draft`；**条目ID等于线索ID，每条已确认线索对应一个分镜**。`participantsConfirmed=true`且`characterIds=[]`表示明确无人出镜。

```json
{
  "clueId": "clue-n1", "name": "入殿陈述", "characterIds": ["char-1"], "participantsConfirmed": true,
  "region": {"x": 0.1, "y": 0.2, "w": 0.5, "h": 0.5},
  "prompt": "保留画作构图，人物衣袖轻动，固定镜头。", "startFrame": "人物立于殿前。", "endFrame": "人物恢复静止。",
  "action": "衣袖轻动", "camera": "固定镜头", "style": "保留古画笔触"
}
```

服务端生成`promptConfigHash`，对`clueId/characterIds/region/participantsConfirmed/style`做SHA-256摘要，确认时核对配置；不要手写伪摘要。参与人物的资料和知识、对应线索均须有效。合并版继续保存这些字段，视频审核与任务另存于workspace.media及video_jobs，不覆盖分镜草稿。

### 检查与发布、欣赏作品

检查清单由`GET /api/projects/{id}/studio/checklist`即时计算，**不单独存成事实表**。AI一致性建议保存在`workspace.consistencyChecks`，格式为`{id,message,resolved}`。

```json
{"ready": false, "videoGenerated": false, "items": [{"id": "knowledge:char-1", "page": "characters", "name": "朱云 · 人物知识", "state": "waiting", "target": "knowledge:char-1", "reason": "等待线索确认", "kind": "entity", "dependency": {"page": "clues", "target": "", "name": "线索库"}}]}
```

立即待办排除`waiting`和运行中任务，但等待项仍阻止整体就绪。欣赏页目前无业务记录、播放状态或作品发布数据，只是独立空页面。

## 4. 版本、写入与任务规则

| 字段 | 含义 |
| --- | --- |
| `project.version` | 项目保存版本；每次项目写入递增，过期写入返回409 |
| `entity.revision` | 条目确认版本；仅草稿保存不递增，确认内容变化时递增 |
| `source.version`、`materialInputs.version`、`imageVersion` | 分别跟踪来源、三段文本整体、图片变更，不能混用 |
| `schemaVersion` | 数据格式版本，不是内容版本；新版工作区为2.0，旧导出外壳仍为1.1 |

保存草稿不替换确认版本；上游发布后，下游保留确认状态并显示版本提醒，可单条或批量复核；撤回恢复最近确认版本。删除通常标记`deleted`，不要直接清理被引用的ID。

条目保存sample，调用`PUT /api/projects/project-1/studio/draft`：

```json
{"version": 12, "kind": "clue", "id": "clue-n1", "data": {"name": "入殿陈述", "type": "narrative", "parentId": "narrative", "plotIds": ["plot-1"], "characterIds": ["char-1"], "content": "朱云入殿，准备陈述。"}}
```

显式生成sample，调用`POST /api/projects/project-1/studio/jobs`：

```json
{"version": 13, "task": "plot_clues", "target": "plot-1", "trigger": "user_button"}
```

文献任务沿用`POST /api/projects/{id}/tasks`。`document_parse`携带`documentId`，PDF上传后自动启动这一本地解析任务；若已有其他任务，文件保留，待用户点击本地解析。`document_analysis`示例：

```json
{"version": 13, "kind": "document_analysis", "targetArtwork": "画甲", "documents": [{"documentId": "document-1", "pages": []}], "trigger": "user_button"}
```

`pages=[]`表示全文，非空为从1开始的PDF页码。模型提案采用接口`POST /api/projects/{id}/documents/analysis/adopt`，示例：

```json
{"version": 14, "analysisId": "analysis-1", "summaryKinds": ["background", "relationships"], "characterIds": ["person-candidate-1"], "updateIds": []}
```

`updateIds`为明确允许更新的现有角色ID；同名但未勾选更新则保留人工资料。采用会将所引页面标为人工采用并同步引用版本，不代表系统独立核实史实。文献任务亦记录模型请求次数及有限的校验诊断，不包含API Key或思考内容。

人物候选手动编辑使用`PATCH /api/projects/{id}/documents/analysis/people/{candidateId}`，携带`version/analysisId/profile`；`profile`仅允许`name/identity/summary/biography/relationships`。保存到候选的`manualProfile/manualEditedAt`，不改写提取原文和引用，也不直接覆盖人物档案。采用时将手动内容写入原角色ID，记录`profileEdit`（创作者编辑、分析及候选ID、时间和字段），并撤销相关确认；原画面称谓仍保存在`sourceName`，用于后续稳定关联。旧版本请求返回409，源文献或分析结果变化时阻止采用过期编辑。

人物`visualHints[].constraintConfirmed=true`才将`strength=required`作为人工硬约束。匹配结果可含`suggestedCharacterId/rejectionReason`，区分模型提出的候选与通过引用校验的对应；`supports`及`constraintChecks`必须关联有效来源或提示。图片上的P编号和模型短C编号只在当前调用中映射回稳定ID，不保存为角色ID。

制作任务使用`state`，图像/OCR任务使用`status`，取值为`queued/running/completed/failed/stale/interrupted`。任务表保存请求、进度、错误；制作任务另记`inputs`摘要、`model/promptVersion/trigger/time`。状态轮询不启动新任务、不递增项目版本；结果应用才保存项目。空响应、失败和过期结果不覆盖原稿。

两类任务统一记录以下字段（摘要示意，不能手写替代实际值）：

```json
{"id": "job-1", "projectId": "project-1", "task": "clue", "target": "clue-n1", "state": "running", "time": "2026-10-31T20:00:00+00:00", "startedAt": "2026-10-31T20:00:01+00:00", "progress": "生成单条线索重生成", "inputHash": "<sha256>", "readSet": ["/workspace/entities/clue:clue-n1/draft"], "writeSet": ["/workspace/entities/clue:clue-n1"], "outputHashes": {"/workspace/entities/clue:clue-n1": "<sha256>"}}
```

实际`readSet`还包括任务使用的资料、人物及创作设置；路径中的`/@ID`表示按ID寻址数组元素。`inputHash`按实际输入计算，`outputHashes`记录输出区域原值。任务完成时重新读取项目，只合并生成差异；修改实际输入或目标才判过期，无关保存／改名不判过期。`inputsChanged`为读取任务时计算的提示值，非另一份事实记录。两张任务表共享事务性互斥，同一项目不得同时提交。

前端轮询采用三方合并，保留未保存编辑；同字段冲突保留本地并展示选择。项目改名使用`PATCH /api/projects/project-1/metadata`，sample为`{"version": 12, "title": "步辇图"}`；只变更元数据、递增项目版本和记日志，不改变条目确认。新建可提交`{"title": "步辇图"}`，去除空白后长度1—120。

读取工作区时`workspace.jobs`是两个任务表合并后的展示投影，以任务表为准；不是业务条目。进入页面、编辑、保存和轮询均不调用LLM。未保存的前端编辑刷新后可能丢失；保存时会生成操作快照。密钥始终只由后端环境读取。

实现依据：`backend/main.py`（持久化）、`backend/workspace.py`（条目与校验）、`backend/studio.py`（任务与接口）。

项目元数据新增`artworkName`保存画作名；`title`为自动分配的唯一显示标题，例如`{"artworkName":"步辇图","title":"步辇图(2)"}`。序号不属于画作名，不影响生成依赖和确认。群体实例标签由前端按`characterId`及实例列表顺序生成，未写入`characters[].name`；多个`annotations`仍共享一份群体人物档案。

## 合并版新增持久化

- `video_jobs(id,project,body)`：独立storyboardId、提示词、依赖／请求指纹、参考计划、输入快照、远端ID、状态及本地视频地址。
- `experience_sessions(id,project,body)`：确认内容签名及collectedClueIds；`experience_turns(id,project,body)`：会话、角色、问题、回答、允许线索、依据、请求去重ID及状态。
- `artwork_catalog/artwork_people/artwork_sources/artwork_relations/artwork_events`：工作台草稿的查询投影，与项目保存同事务更新，不是第二份创作真相。
- `workspace.media[storyboardId]`：保存最终prompt、baseFingerprint、approval及selectedJobId。修改最终文本撤销审核。
- `material:main.draft.paintingInfo`为作品元数据；`historicalEvents`为含时间说明、内容、来源版本和逐字引文的事件列表。
- `relationship`线索的可选`relations`数组包含`fromId/toId/label/sourceId/sourceVersion/quote`；两端须在该线索characterIds中，确认时校验来源和逐字引文。
- 项目根级`archived`用于可恢复归档。原数据库、历史和图片不删除。
